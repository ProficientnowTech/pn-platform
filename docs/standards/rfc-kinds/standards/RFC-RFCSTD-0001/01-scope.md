## 1.1 Purpose

Standards RFCs define how to write RFCs. They establish:

| Aspect | Description |
|--------|-------------|
| Structure | Required and optional sections for a specific RFC kind |
| Formatting | Style and presentation requirements |
| Validation | Criteria for determining compliance |
| Examples | Demonstrations of proper usage |

Standards RFCs are meta-documents—they exist to govern other documents rather than to describe systems or implementations.

---

## 1.2 Applicability

This RFC applies to all Standards kind RFCs, including:

| RFC ID | Title | Status |
|--------|-------|--------|
| RFC-RFCSTD-0001 | RFC Kind: Standards (this document) | Draft |
| RFC-RFCSTD-0002 | RFC Kind: Architecture | Draft |
| RFC-RFCSTD-0003 | RFC Kind: Specification | Draft |
| RFC-RFCSTD-0004 | RFC Kind: Best Current Practice | Draft |

Future Standards RFCs defining new kinds MUST also follow this structure.

---

## 1.3 Audience

| Audience | Role | Primary Sections |
|----------|------|------------------|
| RFC Authors | Create new RFCs | Structure, Formatting, Examples |
| RFC Reviewers | Validate RFC compliance | Validation Criteria, Requirements |
| Governance Bodies | Approve RFC standards | All sections |

---

## 1.4 Non-Goals

Standards RFCs do NOT:

| Non-Goal | Belongs In |
|----------|------------|
| Define system architecture | Architecture RFCs |
| Specify implementation requirements | Specification RFCs |
| Document operational procedures | BCP RFCs |
| Contain working code | Implementation repositories |

---

## 1.5 Conformance

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in BCP 14 [RFC2119] [RFC8174].
