## Why
Definitions, schemas, provisioning scripts, configuration bundles, and Kubernetes deployment tooling are scattered across `infrastructure/modules/bootstrap`, `infrastructure/modules/templates`, `kubernetes/`, `k8s-cluster/`, and `platform/`. Each layer couples tightly to the others, so adding a new infrastructure platform or container orchestrator requires spelunking unrelated directories. There is no single API (or binary) that validates schemas, versioned configuration packages cannot be shared between modules, and the partially built provisioner still relies on bespoke bash entrypoints. This blocks the next phase of work where we must mix platforms (Proxmox + bare metal + cloud), reuse provisioner templates, and onboard business workloads predictably.

## What Changes
- Introduce a top-level `api/` Go CLI that owns schemas, definitions, validation tooling, and generators for inventories/configs that every other module consumes. The CLI replaces the current maze of bash scripts.
- Convert the repository into a Go monorepo with a single root `go.mod`, allowing shared packages/commands to evolve together and enabling tagged GitHub releases for versioned distribution.
- Establish a dedicated `config/` module that stores reusable configuration bundles via manifests and Git releases (not directory names). Each module keeps its own `environments/` folder that references a config package ID instead of duplicating config files.
- Restructure `infrastructure/` into `config/`, `environments/`, and `platforms/<platform>/<provider>/`, migrating today’s Proxmox/Terraform stack into `platforms/proxmox/terraform` while leaving space for bare metal and cloud providers.
- Promote the partially completed image templating system under `infrastructure/modules/templates/provisioner` into a dedicated `provisioner/` module that exposes static-versus-dynamic configuration contracts, consumes both `api/` outputs and configuration references, and publishes image metadata for downstream consumers.
- Create a `container-orchestration/` module with pluggable providers (start with existing Kubespray implementation) that deploy Kubernetes clusters using the inventories generated by `api/` and the hosts delivered by `infrastructure/`.
- Retain `platform/` for platform-level automation but enforce that it only consumes the container-orchestration API, carve business workloads (Helm charts, manifests, GitOps pipelines) into a new `business/` module, and ensure business charts are deployed automatically via an app-of-apps pattern under `business/charts/`.
- Add a `docs/` module that centralizes architectural references, runbooks, module-level documentation, and a scaffolded **fuma-docs** application that will eventually be hosted on the platform.
- Document the end-to-end contract (definitions → config packages → provisioner → infrastructure → container orchestration → platform → business) and limit the MVP to Proxmox/Terraform (infrastructure) + Kubespray (container orchestration) so the refactor ships incrementally. Remote image uploads should be prepared for (metadata, stubs) but not implemented yet.

## Impact
- Specs: adds `repository-modular-architecture` capability describing module responsibilities, APIs, config-versioning rules, and MVP scope.
- Code: relocates bootstrap definitions, templates, and Kubespray assets into new modules; introduces the `api` Go CLI; adds a shared `config/` module; updates Terraform/Kubespray and provisioner to consume API+config outputs; splits platform vs. business assets; adds a `docs/` home.
- Tooling/workflows: engineers call the `api` binary for validation/generation instead of bespoke scripts, provisioner invocations originate from the API, and each module integrates through defined directories/contracts that reference config packages tracked via manifests + Git releases.
